# 两人协作计划

> 本文保留的是工程演进与协作档案，其中的 P1–P4、Code Agent 和任务编号不代表当前产品定位。当前产品以 [产品定义](../product-definition.md)、[需求](../requirements.md) 和 [路线图](../roadmap.md) 为准：面向创作者，以多维证据支撑自然语言控制剪辑。

基线：P1 已完成，提交 `4f92e57`；[P1 验收](../p1-acceptance.md) 是后续回归门槛。本计划组织两人共同开发，产品仍是单人本地使用，不增加多人在线编辑功能。

GitHub 任务链接由 [任务索引](github-index.md) 汇总。任务细节与依赖的初始规划保存在 [tasks.json](tasks.json)；执行进度、认领与评审以 GitHub Issue/PR 为准。

## 分工

| 角色 | 主责 | 当前必做任务数 | 对方负责评审 |
| --- | --- | --- | --- |
| A：媒体与智能 | 素材基准、ASR/视觉、分析管线、初稿规划、外部 Agent 演示、字幕/BGM/构图、模型预算 | 10 | B 评审接口、存储兼容和可调用性 |
| B：平台与交互 | 契约、CI、证据存储/检索、任务、CLI/API、Web、恢复、最终交付 | 10 | A 评审素材语义、编辑效果和实际使用流程 |

没有提前指定真实账号。`owner:A` / `owner:B` 是分工角色；你们各选一个角色，开始某个 Issue 时把自己设为 Assignee。一个人同一时间只主做一个任务，另一人承担短时评审；不单独分出测试岗位。

任务粗估：A 约 10.5–17.5 个有效工作日，B 约 11.5–19.5 个有效工作日，不含可选扩展。它们用于比较负载，不是交付日期；依赖等待、模型选型和评审仍需余量，不能简单将旧单人估算除以二。

## 开始顺序与并行窗口

| 窗口 | A 的主线 | B 的主线 | 汇合条件 |
| --- | --- | --- | --- |
| 0：协作准备 | F01 固定 3 个真实任务 | F02 契约冻结 → F03 CI | 双方确认接口样例与测试基准 |
| 1：分析与存储并行 | P2-02 ASR → P2-03 视觉证据 | P2-01 证据库 → P2-04 检索 | provider 输出与 repository 输入匹配 |
| 2：规划与任务并行 | P2-05 分析管线 → P2-06 初稿 | P3-01 异步任务 → P4-05 恢复 | 有来源的初稿可通过任务导出；分析 handler 在 P2-05 后联调 |
| 3：工具入口 | P4-06 模型配置与预算 | P3-02 CLI/工具 → P3-03 API | 稳定的工具契约及真实 API |
| 4：使用闭环与界面 | P3-04 Agent 连续编辑 → P4-02 字幕 → P4-03 BGM → P4-04 构图 | P4-01 Web | 统一接口完成预览、局部修改、任务和导出 |
| 5：联合验收 | 交叉试用、修媒体/模型问题、演示素材 | P4-07 汇总 8 个任务、修平台问题、交付 | 7/8 真实任务成功且 P1 不变量全部通过 |

里程碑标识验收边界，不要求按 P2→P3→P4 串行开工。尤其 P3-01、P4-05 可以在依赖就绪后提前做，避免 B 等待模型调试。UI 可以先按 API 样例做 mock，不能因此宣称联调完成。

## 模块边界与冲突处理

| 范围 | 默认修改负责人 | 协作规则 |
| --- | --- | --- |
| `internal/analysis/`、`internal/planner/` | A | 通过契约访问 repository/provider，不直接改数据库 schema |
| `internal/catalog/` | B；F02 冻结契约 | A 在独立分析包实现 provider，避免两人修改同一个 Catalog 文件 |
| `internal/store/`、`internal/jobs/`、`internal/app/` | B | migration 编号由 B 分配；A 提交字段需求及样例后由 B 接入 |
| `cmd/video-agent/`、`internal/httpapi/`、`web/` | B | 各入口复用服务，不复制编辑规则；先接口后联调 |
| `internal/media/`、`internal/render/` | A | 分析扩展与字幕/BGM/构图尽量新增独立文件；渲染任务按顺序合并 |
| `internal/domain/`、`internal/edit/`、`internal/agent/` | 共享；按 Issue 约定单个负责人 | 开工前写明准备修改的文件/契约，另一人确认后再动；同一时段不做双向大重构 |
| `integration/` | 功能作者补测试，另一人核验 | 按特性拆测试文件；B 维护 CI 入口 |

这张表是避免冲突的约定，不是权限系统。已有 P1 CLI、revision、锁定、来源范围、幂等和验证发布必须保持；不能为新功能绕开编辑引擎直接写库。

## GitHub 使用方式

1. 先看总任务 Issue 和自己的角色标签，选择 `status:ready` 的任务；把自己设为 Assignee，改为 `status:in-progress`，在 Issue 留下分支和准备修改的文件范围。
2. 分支名：`feat/<任务ID>-<简短描述>`，例如 `feat/P2-02-asr-provider`。从最新 `main` 开始；一个 PR 解决一个可验收任务。
3. 提交 Draft PR 及 mock/契约尽早给对方评审。接口变更先补契约和样例，合并基础 PR 后再合并消费方 PR。
4. 准备合并时改为 `status:review`，PR 写 `Closes #编号`，附验收命令和结果；另一人 review，作者处理意见。约定至少一次非作者评审，但没有擅自设置仓库强制保护规则。
5. 合并后让 PR 自动关闭 Issue；人工检查下游依赖，将满足条件的任务从 `status:blocked` 改为 `status:ready`。标签与总任务勾选不由本计划自动同步。

`status:backlog` 用于 L01/L02 两个可选任务；未共同决定投入前不占用当前 MVP 人力。状态标签一次只保留一个。遇到阻塞，在 Issue 写明缺少什么和可验证的解除条件。

## 每个任务的完成标准

- Issue 中的验收清单逐条有对应代码、测试或真实产物；PR 描述链接证据。
- 功能作者补适当测试，另一人实际运行或核对结果。模型相关功能同时提供无网络 mock 回归和一次真实调用证据，日志脱敏。
- 构建、race、vet 与相关媒体验收通过；涉及渲染/时间线/任务状态时必须显式运行 FFmpeg 验收，不能用跳过来代替。
- 新增 schema 能升级 P1 工程，不丢历史；改变 CLI/API 行为时更新说明和兼容策略。
- 不提交私人视频、数据库、API key；大文件留本地或提供可重现的素材清单。
- 一个任务只有在实际合并并满足验收后才关闭；接口 mock、UI 截图或模型口头“完成”不能单独证明功能完成。

## 里程碑退出条件

- M0：真实任务与契约获得双方确认，CI 能阻止 P1 回归。
- P2：真实素材→证据→检索→初稿→真实 MP4 可复现；不足素材返回 no_match/澄清。
- P3：外部 Code Agent 能创建初稿、连续修改 5 次、恢复版本并导出，且能识别冲突与失败。
- P4：8 个真实任务至少 7 个无需改代码完成，Web/字幕/BGM/构图/预算与恢复有证据，比赛演示可重现。
- Later：MCP 和内置 Agent 分别评估，均不阻塞 P4。
